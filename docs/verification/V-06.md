## Item

OpenCode v2: `execute.before` and `execute.after` fire on success and failure; MCP calls pass through hooks; Harbor installs v2

## Why it matters

v1 has reported hook bugs

## Versions under test

- Harbor 0.24.0, `harbor/agents/installed/opencode.py`
- npm `opencode-ai`: `latest` = 1.18.34, `beta` = 0.0.0-beta-202608110357 (dist-tags read 2026-10-05)
- npm `@opencode-ai/plugin`: `latest` = 1.18.34, `beta` = 0.0.0-beta-19271

## Evidence

1. Harbor installs `npm i -g opencode-ai@<version>` and defaults to `@latest` when no version is given (`opencode.py`, `install`).
2. `opencode-ai@latest` is 1.18.34. Its plugin package exposes the v1 hooks `tool.execute.before` and `tool.execute.after` (`dist/index.d.ts` lines 235 and 249), which SPEC 9.3 excludes because of reported v1 hook bugs.
3. The v2 tool hooks `execute.before` and `execute.after` under `hook` (`dist/promise/tool.d.ts` lines 29, 37, 55) exist only in `0.0.0-beta-*` and `0.0.0-next-*` snapshot builds. No semver v2 release is published.

## Owner decision (2026-10-10)

Option (b): OpenCode runs on the v1 hooks of the pinned semver release, with conformance as the gate (D-0019).

## Hook behavior on 1.18.35 (2026-10-10)

`npm view opencode-ai dist-tags` on 2026-10-10: `latest` = 1.18.35; `beta` and `next` are still snapshot builds.

v1 plugin API (`@opencode-ai/plugin@1.18.35`, `dist/index.d.ts`): `tool.execute.before(input: { tool, sessionID, callID }, output: { args })` and `tool.execute.after(input: { tool, sessionID, callID, args }, output: { title, output, metadata })`. A plugin module may default-export `{ id, server }` (`PluginModule`); OpenCode loads it from the `plugin` array of `opencode.json` as a `file://` URL.

Setup: `node:22-bookworm` (`sha256:0e5f9065...`), `npm i -g opencode-ai@1.18.35`, the built `injector-opencode` layout, and a local fake Anthropic Messages endpoint (`V-06/server.mjs`) that answers each request with one scripted tool call, then a final text, and logs every request body. The tool result the model would read is taken from the next request body. The scripts are in `docs/verification/V-06/`; the full output is `V-06/2026-10-10-result.txt`. No model API was called.

| Probe | Engine record | Tool result in the next model request |
|---|---|---|
| `err` on `read` | apply | `"Error: ETIMEDOUT: operation timed out after 30000ms"`, `is_error: true` |
| `deny` on `bash` | apply | `"Error: resource temporarily unavailable (EAGAIN); command was not started"`, `is_error: true` |
| `trunc` on `read` | apply | first 30 characters of the real output |
| `empty` on `glob` | apply | `""` |
| `trunc` on `grep` | apply | first 30 characters |
| `empty` on `edit` | apply | `""`; the edit is applied on disk |
| `falsefail` on `write` | apply | `"Error: connection reset by peer (ECONNRESET) while reading response"`, `is_error: true`; the file is written |
| `trunc` on `read` of a missing file | apply | the real `File not found` error, unchanged |
| no plugin | none | real output |
| plugin module that throws on load | none | real output (the session runs without the plugin) |

Findings:

1. A hook that throws turns the call into a tool error, in `before` (no side effect) and in `after` (side effect stands). OpenCode prefixes the message with `Error: `: this is the harness's own wrapping and goes in the capability file as attribution, not as a payload difference (SPEC 7.2).
2. `after` mutations of `output.output` reach the model for `read`, `glob`, `grep` and `edit`, including an empty string.
3. On a failed call the real error reaches the model. The engine logged `apply` for that call although nothing was delivered; reconciliation must count it as not delivered, as for the other harnesses.
4. A plugin that fails to load is skipped: fail-open at load time. Inside the hooks the injector catches its own failures and passes the call through, because a throw would become a tool error.
5. The default tool list sent to the model is `bash`, `edit`, `glob`, `grep`, `read`, `skill`, `task`, `todowrite`, `webfetch`, `write`. There is no `list` tool, so `fs.list` reaches OpenCode agents only through `bash`.
6. Under the sandbox, `models.opencode.ai` returned 403, and some runs hung after `init` until the 45 s timeout. Each probe retries up to 3 times; every probe above completed. `OPENCODE_DISABLE_MODELS_FETCH=1` and an explicit model entry in the provider config were set.

Not covered here: MCP tools, which Track N does not use, and the reported v1 bugs against real model traffic. Both are part of model-call conformance.

## Model-call conformance (2026-10-10 and 2026-10-11)

Real runs with `claude-sonnet-5-5`, 3 runs per cell; evidence in `results/conformance/opencode@1.18.35/`.

- The first run (PR #16) scored `deny`, `err` and `falsefail` 0/3 on every class. The injector had applied each fault and the call was blocked, and `agent/opencode.txt` shows the tool part as `"status": "error"` with the catalog text in `state.error` (for example `EACCES: permission denied`). The model's next text quoted that error. Harbor 0.24.0 builds the ATIF observation from `state.output` only, so the trajectory had no result for failed calls and the checker read an empty string.
- `ChaosOpenCode` now copies `state.error` into `output` for error parts before Harbor converts the events. The three types were re-run on 2026-10-11 and pass 3/3 on every exposed class; `parity_set` is all six types.
- `attribution_visible` is false for the text types because the trajectory holds the bare error. The fake-model run above saw OpenCode send the same text to the model with an `Error: ` prefix; the real request bodies are not logged, so the capability file keeps what the trajectory shows.
- A plugin module that throws on load: the session runs without it, `crash_behavior: fail_open`, as in the fake-model run.

## Conclusion

In progress. Every M1 fault type has a delivery path on OpenCode 1.18.35 through the v1 hooks. Model-call conformance closes the item. The earlier analysis follows.

SPEC 9.3 says to support v2 only, on a pinned v2 release, and none exists on npm as of 2026-10-05. The options are:
(a) pin an exact beta snapshot and treat each snapshot bump as a harness version bump that reruns conformance,
(b) run OpenCode on the v1 hooks with conformance as the gate, against SPEC 9.3, or
(c) defer `opencode-claude` until a v2 release ships.
Not yet tested: whether hooks fire on failure and whether MCP calls pass through them. Both need a running binary and a model.
