## Item

Separate verifier and network policy to keep admin endpoints away from the agent

## Why it matters

Outcome validity on Track S

## Versions under test

- Harbor 0.24.0, Docker Compose as installed in the cloud session (Docker Engine with `network_mode` support).
- `datasets/cmca-s` compose files and the images `tt-gateway:0.1.0` and `tt-tickets:0.1.0` built by `scripts/service-images.sh` at this commit.

## Design under test

fx 0.0.13 accepts a plain `http` MCP URL only on loopback; any other host fails with `McpConfigInvalidUrl` (observed in a Harbor trial with `gateway:8000`). So the agent cannot reach a separate gateway container by name over plain HTTP, and the layout is:

- `gateway` runs with `network_mode: "service:main"`: it shares the agent container's network namespace and listens on `127.0.0.1:8000`. It keeps its own filesystem, so its engine config (`/etc/tt`) and its log directory (`/var/log/tt`) are not visible from `main`.
- `tickets-backend` runs with `network_mode: none` and listens on a unix socket in the named volume `tickets-socket`, mounted only by `gateway` and `tickets-backend`. Every request from the agent passes through the gateway.
- The verifier does not call the service. Harbor's `[[artifacts]]` with `service = "tickets-backend"` copies `/var/lib/tickets/state.json` (current tickets plus the full mutation log) out after the agent phase, and `[verifier] environment_mode = "separate"` runs `tests/` in its own image with that file re-materialized. No admin endpoint exists.

## Evidence

From `main`:

```
http://127.0.0.1:8000/tickets/mcp POST initialize -> HTTP 200
http://127.0.0.1:8000/healthz -> HTTP 404
tickets-backend -> gaierror [Errno -2] Name or service not known
gateway -> gaierror [Errno -2] Name or service not known
/run/tickets exists: False
/run/tickets/tickets.sock exists: False
/etc/tt exists: False
/var/lib/tickets exists: False
```

- `tickets-backend`: `NetworkMode` `none`; outbound fetch fails with `EAI_AGAIN`.
- `gateway`: `NetworkMode` `container:<main id>`.
- The gateway serves only `POST /<server>/mcp` paths; everything else is 404.
- In the oracle trials the verifier reads `state.json` and the gateway logs from the artifacts and scores 1; nop scores 0.

## Conclusion

Closed. The agent reaches the tickets service only through the gateway on loopback. It cannot reach the backend, its socket, its state file, the engine config or the injection log. The verifier reads service state from collected artifacts, not from an endpoint.
