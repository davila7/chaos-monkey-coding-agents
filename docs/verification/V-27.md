## Item

D-0040 item 6: on the pinned fork binary inside a container, with fx pointed at a stub model through `FX_GATEWAY_CHAT_URL` (the V-22 method, no model cost): (a) with no `hooks` key, the fork sends the same request bytes as fx 0.0.13 on a scripted session; (b) every built-in tool fires both events with the documented fields; (c) Track N conformance for the six fault types, with the model-visible bytes recorded; (d) the capabilities file emitted from conformance.

## Why it matters

`fxh-claude` lines up with `fx-claude` on Track S only if the fork changed nothing but the interception point (D-0040 item 7). Track N comparisons hold only for fault types in the parity set (D-0040 item 8), and a fault whose framing differs from fx's own output would be visible to the agent.

## Documentation read (2026-10-21)

- `FORK.md` in davila7/fxh#1, which documents the settings schema and the event fields. It follows the Claude Code hooks schema (https://code.claude.com/docs/en/hooks): `hooks.PreToolUse` / `hooks.PostToolUse` groups with `matcher` and `{"type": "command", "command", "timeout"}`; exit code 2 refuses a call with stderr as the message; `hookSpecificOutput.updatedToolOutput` replaces a result. fxh additions: `updatedToolOutputIsError`, and `tool_failed` on PostToolUse events.

## Method

`stub.py` answers fx in the AI Gateway stream format, as in V-22. With `SCRIPT` set it plays a fixed list of tool calls; without it, it plays the calls the conformance probe in the user turn asks for. Each request is saved as `req-<n>.json`. The stub model does not reason, so these runs check what the harness and the injector deliver, not how a model reacts to it.

fx sends plain HTTP only to a loopback gateway URL. With `FX_GATEWAY_CHAT_URL=http://172.17.0.1:8787/v1/chat` it started TLS and failed with `TlsInitializationFailed` (observed 2026-10-21, not in fx's documentation). Items (a) and (b) run the stub inside the same container (`session.sh`). For (c), Harbor runs the agent in its own container, so `v27_agent.StubRelayFxh` starts `relay.cjs` on `127.0.0.1:8787` in the agent container, forwarding to the stub on the Docker host. The relay is the only difference from `ChaosFxh`.

## Evidence

### (a) Track S behavior unchanged

`compare.py` replaces three values that change on every run with either binary (the session id fx sends in headers, the random part of shell replay handle names, shell `duration_ms`) and sorts the requests, because the title request and the model list request run concurrently. Result: `fx-2`, `fxh-1`, `fxh-2` and `fxh-log` each sent 11 requests, identical to `fx-1` after normalization. `fxh-log` shows that a command that answers nothing leaves the requests unchanged too.

### (b) Events and fields

16 events, a PreToolUse and a PostToolUse for each of the eight calls, all with `tool_use_id` matching the model's call id. PreToolUse fields: `cwd`, `hook_event_name`, `session_id`, `tool_input`, `tool_name`, `tool_use_id`. PostToolUse adds `tool_response` and `tool_failed`. `tool_failed` is `false` for seven calls and `true` for `shell` exiting 3, as documented. No `agent_id`: the session started no subagent.

PostToolUse for a call that ran and failed is an fxh decision made during implementation (commit `bfb6caf`, DECISIONS.md D-0040 implementation note 2): without it the injector could not transform the output of a shell command that exits non-zero, the case behind the M5 `cc-claude` delivery gap.

Model-visible bytes (`V-27/2026-10-21-visible.txt`, attempt 0, the trajectory observation of each probed call):

- `deny`, `err`, `falsefail`: fx's own failure frame, `{"error":{"type":"tool_execution_failed","tool_name":"read_file","message":"EACCES: permission denied"}}`, with the catalog message in `message`. fx sends it to the model as error text, the same way it sends a failure of its own.
- `empty`: `read_file` keeps its frame with no lines (`<path>probe/notes.txt</path>\n<content>\n</content>`), as fx shows an empty file; `shell` keeps the JSON object with `output_delta: ""` and `full_output_handle: null`; `write_file`, `edit_file` and `grep_files` return an empty string.
- `trunc`: `read_file` lines stay numbered inside the frame, cut inside line 5; `shell` keeps the object with `output_delta` cut; `grep_files` is cut after the summary line, `[grep] 1 matches for marigold\n - probe/d`.
- `poison`: `read_file` and `shell` show the stale line in place of the real one, inside fx's frame. The `fs.search` probe uses a whole-result replacement (no stale source), so the model sees the replacement text without fx's `[grep]` summary line. Track N tasks declare stale-line poison (D-0037), which keeps the frame.

A first pass, on an earlier build, showed the `grep_files` cut as `probe/d`, without the ` - ` lead of a match line; the injector now keeps the lead when a cut falls inside the `path:N:` prefix (unit test in `packages/injector-fxh`), and the evidence above is from the run after that change.

### (d) Capabilities

`python -m cmca_harbor.conformance report --harness fxh --version 0.0.13-h1 --jobs <jobs>` wrote `capabilities/fxh@0.0.13-h1.json`: `tool_map` `read_file` fs.read, `write_file` fs.write, `edit_file` fs.edit, `grep_files` fs.search, `shell` shell; `parity_set` `deny`, `err`, `empty`, `trunc`, `falsefail`, `poison`, the same set as `claude-code@2.1.289.json`, `pi@1.0.3.json` and `opencode@1.18.35.json`.

## Checker extension

The conformance checker recognizes an `empty`, `trunc` or `poison` result by the text the model sees. fx frames that text: `read_file` returns `<path>..</path>\n<content>\n` with numbered lines, and `shell` returns a JSON object with the output in `output_delta`. The first pass on an earlier build failed `empty` for `fs.read` and `shell` for that reason alone. `conformance.fx_inner` unwraps the two frames before the check (`Harness.inner`, used for every type except `deny`, `err` and `falsefail`); `test_fx_inner_reads_inside_fx_framing` covers it.

## Not covered

- Input corruption (`inarg`) is not among the conformance types for any harness: its weight is 0 (D-0005 item 4, D-0039), so the six types checked are `deny`, `err`, `empty`, `trunc`, `falsefail` and `poison`, the same set as `capabilities/claude-code@2.1.289.json`, `pi@1.0.3.json` and `opencode@1.18.35.json`.
- `glob_files` is not mapped to a class the probes cover; it runs through the injector as `fs.search` only in tasks.
- MCP tools (`mcp_<server>_<tool>`) are not mapped (D-0040 implementation note 3).
- No model-backed run. The probes with `anthropic/claude-sonnet-5.5` through the Vercel AI Gateway need the owner's approval of a cost estimate (CLAUDE.md rule 5).
