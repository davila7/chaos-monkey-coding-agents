## Item

D-0044 item 5: with the pinned Codex binary in a container and a loopback stand-in for the Messages API behind the bridge (no model cost): the bridge round trip, Track N conformance for the six fault types, and the capabilities file.

## Why it matters

Codex speaks only the Responses API to custom providers (D-0044 context), so every `codex-claude` trial depends on the bridge: a mapping error would change what the model sees, and a request that does not repeat the previous one breaks caching and the thinking blocks Claude needs back. Track N rows compare only on fault types in the parity set.

## Method

(a) `V-28/roundtrip/run.sh`: one container with `--network none` runs `roundtrip/mstub.py` (a streaming Messages API stand-in playing `roundtrip/mscript.json`: thinking, text and an `exec_command` call; thinking and an `apply_patch` call; a final text), the bridge pointed at it, and Codex with the provider, catalog and settings `ChaosCodex` writes. `roundtrip/check.py` reads the requests the stand-in received.

(b), (c) `V-28/conformance.sh` runs the conformance plan with `v28_agent.StubCodex`, which differs from `ChaosCodex` only in the bridge's Messages API endpoint and key: `V-28/stub.py` on the Docker host, which plays the calls the probe in the user turn asks for (`exec_command` with the probe's command, `apply_patch` adding `answer.txt` or changing `config.txt`). The stub does not reason, so these runs check what the harness and the injector deliver, not how a model reacts. In this session the containers reach npm and GitHub through a TLS-intercepting proxy, so each run added `--ak extra_ca_cert=<proxy CA>`; the commands were split into three parallel lanes (same commands, same order within a lane).

The bridge was rebuilt with the MCP change below while these jobs ran. The change adds a branch for `namespace` tools only; without MCP servers Codex sends none, and the round trip rerun after the change gave the same result as `roundtrip/2026-10-30-result.txt` except the random chunk id.

### Track S: MCP tools did not reach the model

The first `clean` probe job (2 trials, $0.0606, not counted) exposed no ticket tool: the model answered that only `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource` were available, and the gateway logged no call. A container check with Codex 0.163.0, a stdio MCP server with one `get_ticket` tool, and a loopback server that logs the Responses API request (no model) showed why:

- With `supports_search_tool: true` in the catalog entry (copied from `gpt-5.5`), Codex defers MCP tools and sends a `tool_search` tool (`execution: "client"`) instead. The bridge drops it as a hosted tool.
- With `supports_search_tool: false`, Codex sends `{"type": "namespace", "name": "mcp__tickets", "tools": [{"type": "function", "name": "get_ticket", ...}]}`. The bridge dropped namespaces too.
- Of three `function_call` shapes sent back, only `{"name": "get_ticket", "namespace": "mcp__tickets"}` reached the MCP server (`tools/call`). `mcp__tickets__get_ticket` and `mcp__tickets.get_ticket` got `unsupported call: <name>`.

Fix (commit `2d09653f`): the catalog sets `supports_search_tool` to `false`; the bridge sends each namespace function as `<namespace>__<name>` (the Claude Code form, `mcp__tickets__get_ticket`) and maps a call back to `name` plus `namespace`, in both the output and the replayed input. An end-to-end check through the bridge and the stand-in Messages API, in a container without network, ran one `get_ticket` call on the MCP server and returned its result to the model. Codex frames an MCP result like a command, `Wall time: <s> seconds` then `Output:` and the text.

Harbor 0.24.0 records Codex MCP calls in the trajectory by the bare tool name (`get_ticket`), so `probes_s` now also accepts the bare name (commit `d6e58fb6`).
