## Item

D-0027 put fx on Track S only, because the fx documentation describes no hook on built-in tools. D-0031 item 2 asked for a check of the pinned binary for an undocumented switch that disables, replaces, or intercepts built-in tools, with no model calls.

## Why it matters

A Track N cell needs an interception point in the harness's built-in tool path that can apply the SPEC 7 fault types (deny, err, empty, trunc, poison, and the rest) to one call before or after it runs. Without one, fx has no Track N row and the leaderboard shows the cell as not measurable.

- fx 0.0.13, `https://releases.fx.sh/v0.0.13/fx-linux-x86_64.tar.gz`, sha256 `53a3b30ce1541048f8fa4b42b7bc68161466bb2e3708db104449a58af3807430` (the checksum `cmca_harbor.fx.ARCHIVES` pins). The archive holds `fx` (static, stripped ELF, 13180752 bytes), `LICENSE` and `THIRD_PARTY_NOTICES.md`; no configuration files.
- Harbor 0.24.0 `harbor/agents/installed/fx.py`: default `permission_mode` is `yolo`, which the fx log reports as `permission_mode=yolo` and the docs call `full-access`.
- Containers: `python:3.12-slim` and `debian:bookworm-slim` from `mirror.gcr.io`, all with `--network none`.

## Evidence

- Documentation (read 2026-10-15): the configuration page lists every settings key and environment variable; none is a hook, a tool allowlist, or a way to disable or replace a built-in tool. The tools page lists the built-in tools and describes no wrapping or hooking. The permissions page describes `ask`, `auto` and `full-access`, static `permission` rules (`allow`, `deny`, `ask` by tool name and wildcard pattern, user settings only), and a model reviewer in `auto` mode; it states no external command can decide. The ACP page does not say fx delegates file or terminal operations to the client.
- Strings: the binary contains `PreToolUse`, `pre_tool_use_blocked`, `before_tool_execution`, `after_tool_execution` and `Continue the turn. fx hook context:`, but no settings key or file name ties them to a user-configurable hook. The fx ACP log prints `before_tool_execution` and `after_tool_execution` as trace events for every call. The undocumented environment variables are `FX_E2E_*` and `FX_TERMINAL_TEST_*` test endpoints and delays, `FX_GATEWAY_BASE_URL`, `FX_GATEWAY_CHAT_URL`, `FX_BENCH`, `FX_COMMAND_TEST_*` and `FX_UI_OBSERVE_DIR`; none names a tool switch. The ACP method names present are `initialize` and `session/*`; `fs/read_text_file`, `fs/write_text_file` and `terminal/*` do not appear.
- Live, all five runs: fx sent no request to the ACP client (no `fs/*`, `terminal/*` or `session/request_permission`) although the client advertised the capabilities. `read_file` returned the workspace file (`1\thello`), not the client's `CLIENT-INTERCEPTED`. In `full-access` the shell call ran in the container (`state: completed`, `exit_code: 0`).
- Hooks: no marker file was written in any of the five settings locations.
- Permissions: in `ask` and `code` (ACP mode for `auto`) the shell call went to the reviewer model (`openai/gpt-5.6-luna` on the gateway endpoint). A `caution` answer held the call with fx's own error (`tool_review_held`, "Action held after safety review"); `clear` let it run. `read_file` was not reviewed.

## Conclusion

- fx 0.0.13 has no configuration, flag, environment variable, or ACP capability that disables, replaces, or intercepts a built-in tool call. D-0027 stands: fx is on Track S only, and its Track N cells are "not measurable" with this item as the reason.
- Two adjacent mechanisms exist; neither is a built-in tool hook and this item proposes neither:
  1. A model endpoint proxy (documented custom model connection with a loopback `base_url`, or `FX_GATEWAY_CHAT_URL`) sees every tool result in the next model request and could rewrite it. The call has already run, so deny and falsefail would differ from Track N semantics, and the layer is the model API, which any harness with a base URL setting shares; it is a different track, not fx on Track N.
  2. Under `auto` or `ask`, a proxy answering the reviewer with `caution` holds a call before it runs. Only calls fx chooses to review reach it (shell commands it does not recognize, MCP tools, sensitive writes; not `read_file`), the error text is fx's own review message, and the agent is told it was a safety hold. That is a deny on a subset of calls with a harness-specific message, below the SPEC 6.4 parity bar, and it changes the permission mode Harbor runs fx with (`yolo`).
- Recheck when the fx pin moves past 0.0.13.
