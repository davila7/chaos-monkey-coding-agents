## Item

fx MCP frame limit and the proxy payload cap

## Why it matters

Oversized payloads can drop the MCP connection

## Versions under test

- fx 0.0.13 (`fx --version`), linux x86_64 archive sha256 `53a3b30ce1541048f8fa4b42b7bc68161466bb2e3708db104449a58af3807430`.
- `packages/mcp-fault-proxy` and `packages/mock-services` at this commit, run as local Node processes.
- Model `openai/gpt-5.4-nano` on the AI Gateway free tier (the account has no paid credits yet, see V-08).

## Commands run

1. `tickets` service with the `s-p1-report` fixture plus one ticket (id 999) whose body is 5,000 lines ending in `END-MARKER-4471`; the `get_ticket` result is 220,522 bytes.
2. Gateway in pass-through mode (no engine config, so no cap) in front of it.
3. `fx ask --yolo --json --model openai/gpt-5.4-nano -- "Use the tickets MCP server tool get_ticket with id 999. Reply with the last line of the ticket body, exactly."` with `~/.fx/mcp.json` pointing at the gateway.
4. The gateway with an engine config at base rate 0 (cap enforced) against the same oversized ticket, through the MCP SDK client: `packages/mcp-fault-proxy/test/proxy.test.ts`, "replaces an oversized response with a 413 error".

## Evidence

- fx kept the connection. The session's `tool-results/result-mcp_tickets_get_ticket-*.txt` is exactly 65,536 bytes and ends with `... [mcp tool result truncated for tickets/mcp_tickets_get_ticket: original 220522 bytes; cap is 65536 bytes]`, followed by `"truncated":true,"original_bytes":220522,"cap_bytes":65536`. The model then called fx's `read_tool_result` tool and answered `line 001479 export row ok checksum 011850`, a line inside the kept part, not the real last line.
- Through the capped gateway the client receives `isError: true` with `413 Payload Too Large: response of <n> bytes exceeds the 65536 byte limit`, and the gateway writes an `oversize` record to `gateway.jsonl`.

## Conclusion

Closed. fx 0.0.13 does not drop the MCP connection on an oversized result; it truncates the result to 65,536 bytes with a visible marker. That is harness behavior that would make the same service response arrive differently per harness, so the gateway's 64 KiB cap (SPEC 9.2) stays: a response above it reaches every harness as the same 413 error. Task services keep every response below the cap; the `tickets` service pages search results 5 at a time and the Track S task data has no ticket near the limit, so the cap should never apply in a trial. Any `oversize` record in a trial's `gateway.jsonl` marks a task defect, not a fault.
